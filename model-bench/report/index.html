模型分層派工實測報告：haiku 5.5 能接哪幾列、effort 該開多大、快取吃掉多少

一句話結論

派工表（claude-ops/ops/20-dispatch.md §4）原本把「寫腳本、審查、多來源驗證」放在 mid（sonnet）。兩輪共 228 次、全部機器門檻的實測顯示：這些列加上 agentic 修復，haiku 5.5 在有硬門檻的條件下 n/n 全過，成本是 sonnet 的 1/15 到 1/25，而且沒有比較慢。cheap 層的 effort 該開 high：比 medium 多花 15%，修掉四分之三的失誤；xhigh 零增益、時間 1.7 倍。sonnet 的 low 與 medium 無法區分。長上下文計數留 mid。每次有工具的 claude -p 呼叫帶約 34k token 的固定前綴，暖快取時仍佔單次成本 30–38%，所以小任務先合併再談層級。

問題答案詳見
haiku 能接哪幾列12 列中 10 列（含原本 mid 的寫腳本、審查、多來源驗證、agentic 修復、模糊停下）。接不住：長上下文 inline 計數（5/9）。搜尋盤點要 effort high。07
haiku 的 effortmedium 32/36、high 35/36、xhigh 35/36。high 每次 $0.0050（+15%），xhigh $0.0075（+73%）、中位時間 1.7×。05
sonnet 的 effortlow 33/36、medium 34/36，成本差 1%，thinking 都只有約 150 token；effort 旋鈕在這組任務上沒東西可轉。04
sonnet 比 haiku 差的地方七條格式約束題：haiku 三個 effort 9/9，sonnet 兩個 effort 1/6（第一行就加驚嘆號、行長超限、加逗號）。04
快取有工具 0.85–0.93 命中；無工具短題 0.43–0.59；45k inline 0.01。Claude Code 寫 1 小時快取計 2× 輸入價。inline 大上下文每次重寫快取且永不讀回，佔該次成本 71–95%。06
兩輪花費第一輪 $2.00（haiku $0.11、sonnet $1.89）；第二輪 $6.19（haiku 三臂 $0.61、sonnet 兩臂 $5.58）。03、04

01　研究設計：量派工表，不量模型

公開 benchmark 問「這個模型多強」；這份實測問「我的派工表哪一列可以交給更便宜的層級」。題目的單位因此是派工表的列，不是能力維度；評分只有機器門檻，沒有 LLM 評審；執行路徑是 claude -p（Claude Code harness），因為派工真正走這條路，前綴成本與快取行為只在這條路上量得到。

選擇公開 benchmark 常見作法本實測為什麼
題目來源大量自然任務每題對應派工表一列，外加 4 題第五代能力要改的是那張表
題數數百到數千12每題要能機器判定、雙側校準、幾分鐘內重跑
評分自動、LLM judge 或人評只有機器門檻repo 的 gate-design 規則：閘門只裁它能判定的事
量測對象正確率正確率、牆鐘時間、token 組成、快取命中、成本派工決策是成本／速度／品質三角
裁決輸出排行榜分數每列「最便宜且 n/n 全過的臂」直接可寫回規則表
設計依據（repo 內）派工表 §2 的 answer-shape class A/B/C 決定每題門檻的嚴格度；gate-design.md 的 determinable-only 與兩側校準；red-team/ 的錨點規則（引文逐字才算、捏造即整份作廢）；2026-08-16 「schema-first 契約壓抑調查本身」的量測，所以需要調查的題只給輸出契約不給步驟；sharelib.py 的 leak 樣式決定 fixture 不能含什麼。

每題有 控制組：至少一個已知應過、一個已知應不過，bench.py selftest 對單側缺失直接報錯。兩輪共 51 個控制組。這條規則在第一輪就抓到兩個門檻缺陷（08）。

06　快取與成本結構

觀察數字
有工具的 claude -p 固定前綴（system prompt + 工具 schema）約 34k token；無工具約 3k
有工具任務每次的 token 組成（兩模型相近）cache-read 86–98k（前綴 × 約 3 輪）、cache-write 約 10k、輸出 0.8–1.5k、未快取輸入 <10
成本組成（有工具、暖快取）cache-read 30–38%、cache-write 44–47%、輸出 15–27%；真正的新輸入趨近 0
快取命中率有工具 0.85–0.93；無工具短題 0.43–0.59；45k inline 0.01–0.02
冷啟 vs 連跑rep1 0.74 ／ rep2 0.73：前綴在 1 小時 TTL 內已暖；冷啟成本就是第一次的 34k × 2 倍寫入價
快取省下第一輪 haiku $0.20 → $0.11、sonnet $4.02 → $1.89（全不快取 vs 實付）
寫入計價Claude Code 寫的是 1 小時 ephemeral（cache_creation.ephemeral_1h_input_tokens），計 2× 輸入價；用 1.25× 算低 25%，用 2× 與 CLI 自報 228 列全部吻合到第 4 位
最貴的浪費t11 把 45k 帳本 inline：每次 cache-write 94k、永遠不會被讀回，佔該次成本 71%（haiku）／95%（sonnet）
對派工的意義層級省錢（同題 sonnet ÷ haiku 10–25×），批次省更多：五個 2 秒小任務分五次派，前綴付五次；合成一次派，付一次。順序是：先合併小任務 → 再選層 → 最後才調 effort。重複派工同一大段上下文時，放檔案讓 worker 讀，或留在同一 session。同一批作業裡不要交錯 haiku／sonnet 跑同形狀任務：快取按模型分 namespace，交錯等於各付一次冷啟。

08　方法註記：門檻缺陷、掛住、修正

事件怎麼發現處置
t10 門檻把跑測試產生的 tests/__pycache__ 算成「改了測試」第一輪兩模型 4/4 全判失敗；diff 顯示 test_text.py 未變雜湊忽略 bytecode；補「植入修復＋先跑一次測試」控制組；rejudge 對保留的工作目錄重判，列標 rejudged，token／時間／成本不動
t07 引文比對是子字串，fixture 是硬換行 markdownhaiku 兩次 verdict 全對、句子正確，僅換行被接成空白兩側空白正規化；補「接成一行的引文須 pass」控制組；重判
CLI 掛住 420 s 無任何輸出（t04 haiku@medium r1，turns=0）runner 的 TIMEOUT_S 到期記為 is_error，列保留；路由裁定不受影響（同臂 r3 另有一次真失誤）。這就是派工表 §3 第 3 點「外層 timeout」的實作
第二輪報告初版的 p90 是從各題中位數估的從紀錄實算後不同（sonnet low／medium 的 p90 都 11.6 s）改為實算值；撤回「low 省尾端時間」的說法
成本交叉核對低 25%CLI 自報 vs 1.25× cache-write 重算查出 Claude Code 寫 1 小時快取（2×）；改 pricing.json 後 228 列全部吻合

其他：t07 第一輪的兩次「失敗」與 t10 的四次，在 results/runs.jsonl 裡保留原始 token 與時間數字，只有 verdict 與 details 被重判覆寫並標記。seed 重生成讓 t02 的 ERROR 筆數在 14～21 間變動、t04 的定義數變動、t11 的 gold 變動，通過率沒有因此下降。

10　限制與下一輪

  • 12 題各代表一列，一列內部的變異（寫腳本從 20 行到 2,000 行）只採了一個點；單一注入樣式、單一上下文長度、單一語言對。
  • n=3。公開 benchmark 用數百題換統計力，本實測用重複次數換；四個降級裁定在 n=3、seeded 下成立，但仍是小樣本。
  • 量的是 claude -p 路徑；Agent tool 子代理的前綴大小與快取行為可能不同，未量。
  • mid 層缺深推理題，所以「sonnet@low 即可」只對淺任務成立。
